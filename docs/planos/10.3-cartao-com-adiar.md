# Plano: tarefa 10, etapa 10.3, cartão que expande, com o botão Adiar

## Contexto

A 10.2 deixou a lista de hoje com a caixinha. Na 10.3, tocar no título abre o cartão, que mostra as notas e o botão Adiar (seção 6.2). A API já entrega tudo o que a tela precisa: `GET /tasks/today` traz `notes`, `due_date` e `due_date_locked`, e `POST /tasks/{task_id}/postpone` recebe `{"shown_due_date": ...}` e devolve a tarefa com a `due_date` nova (tarefa 7). Hoje são **620 testes**. Até aqui só li arquivos e contei os testes (`pytest --collect-only`), sem gravar nada.

Sigo o padrão da 10.2: `<template>`, dados só por `textContent`, `app.js` em seções, uma gravação por vez, só o pedido mais recente desenhado. Só mudam os três arquivos do front e a especificação. Sem back-end, sem dependência nova.

## Regra 11: um risco na confirmação do Adiar, para a sua decisão

Você decidiu: o primeiro toque troca o texto do botão para "Confirmar adiar (−25% XP)", e o segundo adia. **O risco:** no Chrome do Android, com `width=device-width` (o nosso `<meta viewport>`), o toque duplo não dá zoom, então dois toques rápidos viram dois cliques. Um toque duplo sem querer no "Adiar" passaria pela confirmação inteira e tiraria 25% do XP, sem volta, que é justamente o que a confirmação quer evitar.

**Proposta:** no primeiro meio segundo depois de o botão virar "Confirmar adiar", o toque é ignorado. Um toque duplo dura menos que isso (no Android, o limite é 300 ms); quem lê o botão e decide confirmar leva bem mais. O botão não fica cinza nem perde o foco nesse meio segundo: só uma variável (`confirmReady`) diz se o toque vale. O resto da sua decisão continua igual. Registro isso nas decisões da 10.3, junto com a sua decisão.

## As decisões

### 1. Abrir e fechar: um cartão aberto por vez, e ele continua aberto quando a lista recarrega

**Um por vez.** Abrir um cartão fecha o que estava aberto. Uma variável só, `openTaskId` (o id da tarefa aberta, ou `null`), guarda o estado. Com vários abertos ao mesmo tempo, a lista viraria uma parede de botões Adiar, e o estado da confirmação ficaria mais difícil de seguir (com um aberto, só um Adiar aparece por vez). O preço: abrir um cartão abaixo de outro aberto faz o de baixo subir um pouco. É o jeito comum dos "acordeões" no celular.

**Continua aberto ao recarregar.** A lista é desenhada de novo depois de toda gravação e quando o app volta do segundo plano. Se o cartão fechasse, concluir outra tarefa fecharia o que você estava lendo. Como `createTaskCard` lê `openTaskId`, o cartão já nasce aberto. Se a tarefa aberta sumiu da lista (foi adiada, excluída, ou o dia virou), `showDay` volta `openTaskId` para `null`, para ela não reaparecer aberta outro dia. A tarefa concluída que estava aberta continua aberta em "Concluídas", sem o Adiar.

**Abrir e fechar não redesenha a lista.** Só muda o cartão: `aria-expanded` no botão do título e `hidden` na parte de baixo. Assim o foco continua no botão tocado.

```js
// Abre o cartão tocado e fecha o que estava aberto. Tocar no cartão aberto só fecha.
function toggleCard(taskId) {
  cancelPostponeConfirmation();
  const previousTaskId = openTaskId;
  if (previousTaskId !== null) {
    setCardOpen(previousTaskId, false);
  }
  if (previousTaskId === taskId) {
    openTaskId = null;
  } else {
    openTaskId = taskId;
    setCardOpen(taskId, true);
  }
}

function setCardOpen(taskId, open) {
  const card = document.getElementById("task-card-" + taskId);
  if (card === null) {
    return;
  }
  card.querySelector(".task-toggle").setAttribute("aria-expanded", open ? "true" : "false");
  card.querySelector(".task-details").hidden = !open;
}
```

**O botão do título:** é um `<button type="button" class="task-toggle" aria-expanded="false">` que envolve o título, o ✎, a data da atrasada e o "+N XP". A área de toque fica grande (a largura do cartão, com 48 px de altura no mínimo), e o leitor de tela lê "Ler 30 páginas, Tem notas., botão, recolhido". A caixinha continua fora dele, no `<label>` da 10.2.

**Conceito novo:** `aria-expanded` é um atributo que diz ao leitor de tela se o botão está com a parte dele aberta ("expandido") ou fechada ("recolhido"). O navegador não muda nada sozinho: quem atualiza o valor é o JavaScript.

### 2. O que o cartão aberto mostra

| Tarefa | Mostra |
| --- | --- |
| Pendente com notas | as notas e o Adiar |
| Pendente sem notas | só o Adiar (seção 6.2) |
| Pendente travada | as notas, se houver, o Adiar bloqueado e o texto da trava (decisão 5) |
| Concluída com notas | só as notas |
| Concluída sem notas | "Sem notas.", em texto secundário |

- **Notas com as quebras de linha:** entram por `textContent` num `<p class="task-notes">`, com `white-space: pre-wrap` no CSS, que mostra as quebras de linha e os espaços como foram escritos. Com `overflow-wrap: anywhere`, uma palavra comprida quebra em vez de empurrar a tela para o lado.
- **"Sem notas." na concluída sem notas:** sem ele, o cartão abriria vazio, porque o Editar só chega na tarefa 11. É provisório: sai na tarefa 11, quando o Editar ocupar esse lugar. Registro no "Fora da etapa 10.3".

**Conceito novo:** `white-space` diz ao navegador o que fazer com quebras de linha e espaços do texto. O padrão junta tudo numa linha só; `pre-wrap` mantém como está e ainda quebra a linha no fim do cartão.

### 3. A confirmação do Adiar (decisão sua, já tomada)

- **Primeiro toque:** o texto vira "Confirmar adiar (−25% XP)", com a classe `is-confirming` (fundo na cor de aviso, texto branco, contraste de 4,7 para 1). O "−25% XP" é texto fixo, numa constante, sem conta.
- **Segundo toque, depois do meio segundo da regra 11:** adia.
- **Volta ao normal sozinho** depois de 5 segundos, num `setTimeout`.
- **Volta ao normal ao tocar em outra coisa:** um ouvinte de `click` no `document` cancela a confirmação se o toque não foi no próprio botão. O toque que iniciou a confirmação chega ao `document` depois do ouvinte do botão, com o alvo igual ao botão, e por isso não cancela. Abrir ou fechar um cartão e redesenhar a lista também cancelam.
- **Sem caixa de diálogo do navegador:** nada de `confirm()` ou `alert()`.

```js
// Os textos do botão. O "−25% XP" é fixo: cada adiamento tira 25% (seção 4.2), e a tela não faz conta.
const POSTPONE_LABEL = "Adiar";
const POSTPONE_CONFIRM_LABEL = "Confirmar adiar (−25% XP)";
// Quanto tempo a confirmação espera antes de voltar ao normal, e quanto tempo ignora o toque.
const POSTPONE_CONFIRM_TIMEOUT_MS = 5000;
const DOUBLE_TAP_GUARD_MS = 500;

// O botão que está pedindo confirmação, ou null.
let confirmButton = null;
// Falso no primeiro meio segundo: o segundo toque de um toque duplo não confirma (regra 11).
let confirmReady = false;
let confirmTimer = null;
let readyTimer = null;

function handlePostponeClick(task, button) {
  if (confirmButton !== button) {
    startPostponeConfirmation(button);
    return;
  }
  if (!confirmReady) {
    return;
  }
  cancelPostponeConfirmation();
  postponeTask(task);
}
```

`startPostponeConfirmation` troca o texto, põe a classe e liga os dois `setTimeout`. `cancelPostponeConfirmation` desliga os dois com `clearTimeout`, volta o texto e a classe e põe `confirmButton = null`.

**Conceitos novos:** `setTimeout(função, ms)` roda a função uma vez, depois desse tempo, e devolve um número que `clearTimeout` usa para desistir; um ouvinte no `document` recebe todo clique da página, porque o clique "sobe" do elemento tocado até o `document` (isso se chama *bubbling*), e `event.target` diz onde ele começou.

### 4. Adiar de verdade e o aviso com a data nova

```js
async function postponeTask(task) {
  saving = true;
  disableTaskControls();
  hideMessages();

  let postponed = null;
  let refused = false;
  try {
    // A data que veio da lista. A data nova é o servidor quem calcula (tarefa 7).
    postponed = await apiRequest("tasks/" + task.id + "/postpone", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ shown_due_date: task.due_date }),
    });
  } catch (error) {
    if (error.status === 409) {
      refused = true;
    } else {
      console.error(error);
      showSaveMessage(SAVE_ERROR_TEXT);
    }
  }

  saving = false;
  await refreshScreen();

  if (postponed !== null) {
    showPostponeNotice(postponed);
  }
  if (refused && reloadDidNotExplain(task)) {
    showSaveMessage(LAST_DATE_TEXT);
  }
  focusCardToggle(task.id);
}
```

- **A data enviada** é a `due_date` que veio na lista, e a tela nunca calcula a data nova. `fetch` no modo padrão, como pede a seção 6.7, agora com corpo em JSON.
- **Depois do sucesso**, a lista e o topo recarregam juntos, com o `refreshScreen` da 10.2. O topo não muda (adiar não mexe no XP), mas recarregar os dois mantém um caminho só.
- **O aviso:** uma linha nova no topo fixo, `#postpone-notice` (`role="status"`, cor normal, não de erro), ao lado da mensagem de erro da 10.2: **"Adiada para 06/11/2026: Ler 30 páginas"**. A data vem da resposta (`postponed.due_date`), só formatada pelo `formatDueDate` da 10.2. O título vai junto porque o cartão some da lista e o aviso precisa dizer qual tarefa foi. Fica no topo fixo pelo mesmo motivo da mensagem de erro: ser visto com a lista rolada. Some sozinho em 10 segundos ou na próxima gravação.
- **Uma gravação por vez:** `disableAllCheckboxes` vira `disableTaskControls` e bloqueia também os botões Adiar. Cada cartão novo nasce com o Adiar em `disabled = saving || task.due_date_locked`. Os botões do título continuam livres, porque abrir e fechar não grava nada. O toque duplo no "Confirmar adiar" manda um pedido só: o segundo toque encontra o botão bloqueado.
- **Mensagens:** `hideSaveMessage` vira `hideMessages`, que esconde a mensagem de erro e o aviso do Adiar; a caixinha passa a chamá-la. `showSaveMessage` passa a receber o texto, porque agora há dois (`SAVE_ERROR_TEXT` e `LAST_DATE_TEXT`).
- **Foco:** depois de recarregar, se a tarefa continua na lista (erro ou 409), o foco volta ao botão do título dela. Se ela saiu (o sucesso), não faz nada, como o `focusTask` da 10.2.

### 5. Tarefa travada: o Adiar bloqueado, com o motivo

Quando `task.due_date_locked` vem `true`, o Adiar fica `disabled` e aparece embaixo dele, em texto secundário: **"Data travada: esta tarefa chegou ao limite de adiamentos."** O texto fica no `<template>`, e o JavaScript só tira o `hidden`. Não cita o número 3, para não virar um segundo lugar com a regra: se a constante de `xp.py` mudar, o texto continua certo. E "limite de adiamentos" vale também para a travada por dias de atraso, porque cada dia de atraso conta como um adiamento (seção 4.2).

O botão bloqueado com `disabled` sai da ordem do Tab, e o texto fica logo ao lado, para quem vê e para o leitor de tela, que lê os dois em sequência.

### 6. Os 409

**Tela desatualizada:** recarrega sem mensagem, como na caixinha.

**Última data possível (`9999-12-31`):** a tela não sabe qual 409 recebeu sem ler o texto da resposta, e a 10.2 decidiu reconhecer o 409 sem ler texto. Mas ela consegue ver, **depois de recarregar**, se o recarregamento explicou a recusa. Pelas recusas da rota (tarefa 7), cada 409 deixa um rastro diferente na lista nova:

| A recusa | Depois de recarregar |
| --- | --- |
| tarefa concluída | ela está em "Concluídas", sem Adiar |
| data travada | ela volta com `due_date_locked` (a trava nunca se desfaz sozinha) |
| tela desatualizada | ela sumiu, foi para "Concluídas" ou voltou com outra `due_date` |
| **última data possível** | **ela volta igual: pendente, com a mesma `due_date` e sem trava** |

Então, se depois do 409 a tarefa continua pendente, com a mesma data e sem trava, a única recusa que sobra é a da última data. A tela mostra então, na linha de erro do topo: **"Esta tarefa já está na última data possível e não pode ser adiada."**

```js
// A última lista desenhada, ou null se a última busca deu erro.
let shownDay = null;

// Depois de um 409 e da lista recarregada: se a tarefa continua pendente, com a mesma data e
// sem trava, recarregar não explicou a recusa. Pelas recusas da rota, só sobra a última data.
function reloadDidNotExplain(task) {
  if (shownDay === null) {
    return false;
  }
  for (const listed of shownDay.overdue.concat(shownDay.pending)) {
    if (listed.id === task.id) {
      return listed.due_date === task.due_date && !listed.due_date_locked;
    }
  }
  return false;
}
```

- **Sem conta de data:** `listed.due_date === task.due_date` compara dois textos que vieram do servidor, sem somar nem subtrair dia. O JavaScript nunca escreve `9999-12-31`.
- **Sem ler texto:** a decisão vem do `status` e da lista nova, como na 10.2.
- **Por que não um campo novo na API** (por exemplo, `can_postpone`): mexeria no back-end numa etapa só de front, contra os arquivos da 10.3, e por um caso que, na tela de hoje, só acontece se hoje for 31/12/9999. A conta abaixo é do front, curta, e serve de rede para qualquer 409 que recarregar não resolva.
- **Por que não deixar mudo:** o botão pareceria quebrado, sem dizer nada, toque após toque.
- **Quando acontece de verdade:** na tela de hoje, nunca antes de 31/12/9999. Na 10.4, só navegando dia a dia até lá. O roteiro tem um passo que simula esse dia num servidor à parte, sem tocar no seu banco.
