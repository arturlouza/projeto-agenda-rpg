# Plano da etapa 5.1: tipos ordenados por `created_at`

## Contexto

A seção 6.1 da especificação diz que os tipos são listados por `created_at`, com o id só como desempate. Hoje a tabela `TaskType` não tem essa coluna e a listagem ordena por id. A seção 6.6 explica o problema: o id é só um identificador, e o SQLite reaproveita números. Esta etapa vem primeiro na tarefa 5 porque é a única que muda uma tabela.

## O que eu conferi

- Hoje passam 72 testes.
- O `agenda.db` está vazio (0 linhas nas três tabelas) e fora do Git (`*.db` no `.gitignore`). Apagá-lo não perde nada.
- O `create_all` não altera tabela existente. Sem apagar o banco, o `GET /task-types` vai falhar com `no such column`.
- Um campo `datetime` usa `UTCDateTime` e vai para o JSON com `Z` no fim, por exemplo `2026-01-01T00:00:00Z`.
- No SQLite, o empate sai em ordem de id mesmo sem o desempate no `ORDER BY`.

## Alterações

### 1. `backend/app/models.py`

Nova coluna em `TaskType`, igual à de `Task` e `XpEntry`:

```python
created_at: datetime = Field(default_factory=utc_now)
```

### 2. `backend/app/routers/task_types.py`

Troca o comentário e a ordenação da listagem:

```python
# A ordem de criação vem do created_at. O id só desempata, em caso de empate exato.
@router.get("")
def list_task_types(session: SessionDep) -> list[TaskType]:
    return list(session.exec(select(TaskType).order_by(TaskType.created_at, TaskType.id)).all())
```

`TaskTypeInput` não muda. Como ele só tem `name`, quem chama a API não consegue escolher o `created_at`.

### 3. `backend/tests/test_task_types.py`

- **Ajustar `test_rename_changes_the_name`:** a resposta ganha um campo, então o teste passa a comparar também o `created_at`. Assim ele prova ainda que renomear não muda a data, de que a ordem depende.
- **Novo `test_list_shows_created_at`:** o `GET /task-types` mostra o `created_at` em UTC (termina em `Z`).
- **Novo `test_list_orders_by_created_at_not_by_id`:** o tipo de id 2 com data mais antiga vem antes do tipo de id 1.
- **Novo `test_list_breaks_created_at_tie_by_id`:** com a mesma data, a resposta vem em ordem de id. Um comentário registra o limite: no SQLite, este teste não detecta a remoção do desempate.

Os dois testes de ordem gravam direto no banco, porque a API não aceita `created_at`. Eles usam ids explícitos, para não depender de como o banco gera ids (seção 6.1), e datas com fuso, porque o `UTCDateTime` recusa data sem fuso.

### 4. `docs/especificacao.md`: critério "Pronto quando" da etapa 5.1

Na seção 10, troco só o trecho do empate. O novo critério fica assim:

> **Pronto quando:** um teste prova que a ordem vem do `created_at` (um tipo com id maior e data mais antiga vem primeiro) e que o empate aparece em ordem de id (no SQLite, esse teste não detecta a remoção do desempate); `GET /task-types` mostra o `created_at`; todos os testes passam.

O `CLAUDE.md` não muda: com o critério corrigido, não há exceção a registrar, e o comentário no teste documenta o limite do SQLite.

## Como testar

Pare o Uvicorn antes (Ctrl+C), porque o Windows não apaga um arquivo em uso. No PowerShell, com o ambiente virtual ativo:

```powershell
cd backend
pytest
Remove-Item .\agenda.db
uvicorn app.main:app --reload
```

- **`pytest`:** deve mostrar `75 passed` (os 72 de hoje mais os 3 novos).
- **No navegador:** abra `http://localhost:8000/docs`, crie dois tipos com `POST /task-types` e rode `GET /task-types`. Os dois devem vir na ordem em que foram criados, cada um com o `created_at` terminando em `Z`.
- **Horário:** o `created_at` aparece em UTC, então fica 3 horas à frente do horário de Brasília. Isso é o esperado.
