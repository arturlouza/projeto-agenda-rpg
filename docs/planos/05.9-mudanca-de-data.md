# Plano da etapa 5.9: mudança de data na edição

## Contexto

O `PUT /tasks/{task_id}` da 5.8 edita tudo, menos a data. Esta etapa faz a edição exigir `due_date` e aplica as regras da seção 4.2 e o "mesmo valor" da seção 6.1. Ela fecha a tarefa 5. As regras de contagem já existem em `rules/xp.py` desde a 5.3 e não mudam. Falta usá-las na rota.

## Ponto para você decidir: antecipar tarefa travada por atraso

Os pontos 1 e 6 do seu pedido se chocam em um caso. O "Pronto quando" também diz "travada por atraso (...) recusa até antecipar (409)".

- Uma tarefa travada **por atraso** tem data marcada anterior a hoje.
- Antecipar é escolher uma data ainda mais antiga, então a data nova também é anterior a hoje.
- Como "data anterior a hoje" vem antes de "data travada", esse pedido dá **422, nunca 409**.

O plano da 5.3 já tinha notado isso: "uma tarefa atrasada não consegue ser antecipada". A data não muda em nenhum dos dois casos, e só o código da recusa é diferente.

| Tarefa travada | Data nova | Resposta |
| --- | --- | --- |
| Por adiamento manual, com data futura | Antes da atual, hoje ou depois | 409 |
| Por adiamento manual, com data futura | Anterior a hoje | 422 |
| Por atraso | Hoje ou depois | 409 |
| Por atraso | Antes da atual (sempre anterior a hoje) | 422 |

**O que o plano faz:** segue a ordem da decisão da 5.8 (422 antes de 409). O teste "antecipar dá 409" usa a tarefa travada por adiamento manual com data futura, e um teste separado registra o 422 da travada por atraso. O texto do "Pronto quando" é ajustado para dizer isso (seção 3 abaixo). Colocar a trava antes da data passada daria 409 nos dois casos, mas quebraria a decisão da 5.8. Se preferir assim, me diga ao revisar o plano.

## Ordem das conferências no PUT (ponto 1)

| # | Conferência | Resposta | Quando se aplica |
| --- | --- | --- | --- |
| 0 | Dados do pedido: campos, formatos, id da rota | 422 | Sempre. O FastAPI faz isso antes de a rota rodar |
| — | Tarefa existe? | 404 | Sempre |
| 1 | Data anterior a hoje | 422 | Só se a data mudou |
| 2 | Tipo inexistente | 422 | Se o tipo não for nulo |
| 3 | Tarefa concluída | 409 | Se a dificuldade ou a data mudou |
| 4 | Data travada | 409 | Só se a data mudou |
| 5 | Cálculo do contador | não recusa | Só se a data mudou |
| 6 | Gravar | 200 | Nenhuma conferência recusou |

A busca da tarefa (404) não estava na sua lista, mas precisa vir antes do passo 1: sem a tarefa, não dá para saber se a data mudou. A tarefa só é alterada depois de todas as conferências, então um pedido recusado não grava nada.

## O que muda

### 1. `backend/app/routers/tasks.py`

**`TaskUpdate` ganha `due_date: date`, sem valor padrão.** Assim, o campo é obrigatório na edição. `TaskInput` herda o campo, então a linha repetida sai de lá. Os comentários das duas classes são ajustados.

**Duas funções novas (ponto 5), ao lado de `ensure_task_type_exists`:**

```python
# Responde 422 se a data for anterior a hoje em Brasília. Vale só para data nova.
def ensure_date_is_not_past(day: date) -> None:
    if day < app_today():
        raise HTTPException(
            status.HTTP_422_UNPROCESSABLE_CONTENT, detail="A data não pode ser anterior a hoje."
        )


# Muda a data de uma tarefa, para a edição e para o botão Adiar (tarefa 7). Quem chama já
# conferiu que a data é outra e que não é anterior a hoje. A trava vem antes do contador,
# porque postponements_after_date_change não a confere. Os dias de atraso podem sair negativos
# aqui, com a data no futuro: as regras de xp.py tratam esse valor como 0.
def change_due_date(task: Task, new_due_date: date) -> None:
    if task.completed:
        raise HTTPException(
            status.HTTP_409_CONFLICT, detail="Desmarque a tarefa antes de mudar a data."
        )

    days_late = (app_today() - task.due_date).days

    if is_due_date_locked(task.postponements, days_late):
        raise HTTPException(
            status.HTTP_409_CONFLICT, detail="A data desta tarefa está travada e não pode mudar."
        )

    task.postponements = postponements_after_date_change(
        task.postponements, days_late, task.due_date, new_due_date
    )
    task.due_date = new_due_date
```

**Por que `change_due_date` fica em `tasks.py`, e não em `rules/xp.py`:**

- `xp.py` só tem contas puras: recebe números e datas e devolve um resultado, sem depender de relógio, banco ou HTTP (decisão da 5.3).
- Esta função lê o relógio, altera a `Task` e responde com códigos HTTP. Nenhuma regra de XP é escrita nela: ela só chama as de `xp.py`, então a regra 9 continua valendo.
- A rota do Adiar é uma rota de tarefas e deve ficar neste arquivo. Ela só precisará chamar a função, e nada dela entra agora.

**Por que são duas funções, e não uma:** o tipo inexistente (passo 2) fica entre a data passada (passo 1) e os 409 (passos 3 e 4). Uma função única não permitiria a ordem que você pediu. A tarefa 7 vai chamar as duas, nesta sequência.

**Trava (ponto 3):** a conferência fica em `change_due_date`, que a rota chama, e vem antes de `postponements_after_date_change`. `xp.py` não muda. Os dias de atraso vêm de `app_today()`, em Brasília. Não repito o `max(..., 0)` na rota, porque `effective_postponements` já faz isso. Tanto a trava quanto o contador passam por ela, e o teste de 3 adiamentos com data 5 dias à frente protege esse caso.

**A rota fica assim:**

```python
def update_task(task_id: TaskId, task_update: TaskUpdate, session: SessionDep) -> Task:
    task = get_task_or_404(session, task_id)

    # Mandar a data que a tarefa já tem não é mudança, então nenhuma regra de data se aplica.
    date_changed = task_update.due_date != task.due_date

    if date_changed:
        ensure_date_is_not_past(task_update.due_date)

    if task_update.task_type_id is not None:
        ensure_task_type_exists(session, task_update.task_type_id)

    if task.completed and task_update.difficulty != task.difficulty:
        raise HTTPException(
            status.HTTP_409_CONFLICT, detail="Desmarque a tarefa antes de mudar a dificuldade."
        )

    if date_changed:
        change_due_date(task, task_update.due_date)

    task.title = task_update.title
    # o resto continua igual à 5.8
```

**"Mesmo valor" (ponto 2):** o `date_changed` protege as regras de data. Uma tarefa atrasada, travada ou concluída que recebe a mesma data edita o título normalmente, sem somar atraso ao contador. Repetir o mesmo `PUT` também não conta um novo adiamento, porque na segunda vez a data já é a mesma.

**"Recusa até antecipar" (ponto 4):** o plano segue "recusa inclusive antecipar". `is_due_date_locked` é conferida sem olhar a direção da mudança, então nenhuma data diferente passa pela trava. A única variação é o código da tabela acima.

**Ajustes pequenos no mesmo arquivo:**

- `create_task` passa a usar `ensure_date_is_not_past`, com o mesmo comportamento. Assim, a mensagem fica escrita uma vez só. O teste de criação protege essa troca.
- O texto do 409 em `responses` passa a citar também a data.
- Entra o import de `is_due_date_locked` e `postponements_after_date_change`.

**Conceito novo: subtrair datas.** `date - date` devolve um `timedelta`, a diferença entre as duas, e `.days` dá essa diferença em dias. Se a data marcada estiver no futuro, o número sai negativo.

## Como testar

Na raiz do projeto:

```powershell
.venv\Scripts\Activate.ps1
cd backend
pytest tests/test_tasks.py
pytest
uvicorn app.main:app --reload
```

Os dois `pytest` devem terminar sem falhas. Depois, em `http://localhost:8000/docs`:

1. Com `POST /tasks`, crie uma tarefa com data de hoje e anote o `id`.
2. Com `PUT /tasks/{task_id}`, mude a data para o dia seguinte. Use este corpo, trocando a data:
   ```json
   {"title": "Título novo", "notes": null, "difficulty": "easy", "color": "#F5E6C8", "task_type_id": null, "due_date": "AAAA-MM-DD"}
   ```
   A resposta deve ser 200, com `postponements` igual a 1.
3. Repita o pedido com a mesma data. `postponements` continua em 1.
4. Mude a data para depois mais duas vezes. `postponements` chega a 3.
5. Tente outra data posterior: deve dar 409.
6. Tente uma data entre hoje e a data atual da tarefa: também deve dar 409, porque antecipar não passa pela trava.
7. Tente a data de ontem: deve dar 422, porque o dado é conferido antes do estado.
8. Mande a data atual com outro título: deve dar 200, com o título novo.
9. Tire `due_date` do corpo: deve dar 422.
10. Com `GET /tasks/day/{day}`, confira a tarefa no dia novo.

Tarefa concluída e tarefa atrasada só aparecem nos testes, porque a API ainda não as cria.

**Pronto quando:** todos os testes passam e os passos acima dão o resultado descrito.
