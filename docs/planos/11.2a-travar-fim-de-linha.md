# 11.2a — Travar o fim de linha LF

## Contexto

Na 11.1, o `test_tasks.py` ficou com CRLF porque um `write_text` no Windows troca cada `\n` por `\r\n`. Hoje o repositório está limpo por dentro (os 63 arquivos com `i/lf`), mas nada impede que isso volte a acontecer: este computador tem `core.autocrlf=true` (vem do `C:/Program Files/Git/etc/gitconfig`), e dois arquivos já estão com CRLF na pasta:

- `frontend/css/style.css` (355 CRLF, nenhum `\r` solto);
- `docs/planos/10.2-lista-de-hoje.md` (381 CRLF, nenhum `\r` solto).

Conferi sem alterar nada: trocando `\r\n` por `\n` nesses dois arquivos, os bytes ficam **idênticos** ao que está no `HEAD`. Ou seja, a conversão não muda nenhum outro caractere.

Objetivo: um `.gitattributes` que trave LF no repositório e na pasta, em qualquer computador, mais a regra no `CLAUDE.md` para eu não gravar CRLF de novo.

## Passo 1 — Criar `.gitattributes` na raiz (novo)

```gitattributes
# Fim de linha: o Git decide sozinho o que é texto, e todo texto
# entra no repositório com LF e sai na pasta com LF, em qualquer
# computador, mesmo com core.autocrlf=true
* text=auto eol=lf

# Binários: o Git nunca mexe nos bytes nem mostra diferença linha a linha
# Imagens e ícones do PWA (tarefa 14)
*.png binary
*.jpg binary
*.jpeg binary
*.gif binary
*.webp binary
*.ico binary
# Fontes locais (tarefa 13)
*.woff binary
*.woff2 binary
*.ttf binary
*.otf binary
# Banco SQLite: já fica fora pelo .gitignore; esta linha é uma segunda proteção
*.db binary
```

Notas:
- `binary` é um atalho para `-text -diff -merge`: sem conversão de fim de linha, sem diff de texto, sem tentativa de juntar versões.
- `.svg` fica **de fora** de propósito: SVG é texto (XML), então cai no `* text=auto eol=lf` e ganha LF, como os outros.
- O `text=auto` já detecta binários sozinho; as linhas `binary` são uma garantia explícita para os tipos que sabemos que vêm.

## Passo 2 — Converter os dois arquivos para LF com `write_bytes`

Script temporário no scratchpad (fora do projeto), rodado com `python -I`. Para cada um dos dois arquivos:

1. lê os bytes (`read_bytes`);
2. **para** com erro se houver `\r` solto (que não faça parte de `\r\n`) — assim nada além do fim de linha muda;
3. troca `b"\r\n"` por `b"\n"`;
4. **para** com erro se o resultado não for byte a byte igual a `git show HEAD:<arquivo>`;
5. só então grava com `write_bytes`.

Nada de `git checkout`, `git restore` ou `git reset`.

**Prova de que o conteúdo não mudou:** `git diff -- frontend/css/style.css docs/planos/10.2-lista-de-hoje.md` vazio. Aviso honesto: com `core.autocrlf=true`, esse `git diff` **já sai vazio hoje**, antes da conversão, porque o Git normaliza o CRLF ao comparar. Então ele não basta sozinho como prova. A prova forte é o item 4 do script (bytes iguais ao `HEAD`) mais o `w/lf` no `git ls-files --eol`. Mostro as três coisas.

## Conferências antes de entregar

1. `git ls-files --eol` → todos com `i/lf  w/lf  attr/text=auto eol=lf`. Mais `git ls-files --eol --others --exclude-standard` para os arquivos novos ainda fora do Git (`.gitattributes` e o plano renomeado), que também precisam estar `w/lf`.
2. `git check-attr -a -- icone.png fonte.woff2 agenda.db desenho.svg` → os três primeiros saem `binary`, o `.svg` sai `text: auto` + `eol: lf` (o `check-attr` aceita nomes que ainda não existem).
3. `git status` → só aparecem: `.gitattributes` (novo), `docs/planos/11.2a-travar-fim-de-linha.md` (novo), `CLAUDE.md` e `docs/especificacao.md` (alterados). Os dois arquivos convertidos **não** aparecem, porque o conteúdo no Git não mudou.
   - **Resultado diferente do previsto:** os dois aparecem como ` M`. O conteúdo é idêntico (o hash do arquivo na pasta, com e sem filtros, é igual ao do índice, e o `git diff` sai vazio). O `M` vem só do tamanho guardado no índice, que ainda é o do arquivo com CRLF: quando o tamanho muda, o `git status` marca o arquivo sem reler o conteúdo. Numa cópia do índice no scratchpad, um `git add` dos dois não registrou mudança nenhuma (`git diff --cached` vazio) e eles sumiram do status. No `git add` do commit, acontece o mesmo.
4. **`git add --renormalize` mudaria algo?** Sem rodar o `add`: o `--renormalize` pega o conteúdo que já está no índice e passa de novo pelo filtro de fim de linha. Faço exatamente essa conta, só lendo, no Git Bash:
   ```bash
   git ls-files -s | while read mode oid stage path; do
     novo=$(git cat-file blob "$oid" | git hash-object --stdin --path "$path")
     [ "$novo" = "$oid" ] || echo "MUDARIA: $path"
   done
   ```
   O `hash-object` sem `-w` só calcula o hash, não grava nada. Saída vazia = o renormalize não mudaria nenhum arquivo, e o histórico fica intacto. (Espero vazio, porque todos já estão `i/lf`.)
5. `pytest` (dentro de `backend`) → `659 passed`.
6. Conferência de segredos (regra 14) nos arquivos novos e alterados.

## O que muda para você no Windows (resumo para a entrega)

- **Checkout** (clonar, trocar de branch, `git restore`): os arquivos de texto chegam na pasta **com LF**, mesmo com `core.autocrlf=true`. O `eol=lf` do `.gitattributes` vale mais do que o `core.autocrlf` da máquina, e vale para qualquer computador que clonar o repositório.
- **Commit:** se algum arquivo estiver com CRLF na pasta, o Git converte para LF ao fazer o `git add`. No repositório sempre entra LF.
- **O aviso "LF will be replaced by CRLF" some**, porque o Git não vai mais converter LF em CRLF na saída. No lugar, se algum programa gravar CRLF, pode aparecer o aviso contrário: "CRLF will be replaced by LF the next time Git touches it". Ele é inofensivo: quer dizer que o repositório recebe LF, mas o arquivo na pasta continua CRLF até ser regravado (por isso a regra 15).
- O VS Code respeita o fim de linha de cada arquivo que abre; só arquivo **novo** criado nele pode nascer com CRLF (o padrão no Windows). Como quem cria os arquivos sou eu, com o Write, isso não deve acontecer; e, se acontecer, o commit entra com LF mesmo assim.

## Riscos (regra 11)

- Nenhum arquivo do histórico muda: todos já estão `i/lf` (a conferência 4 prova).
- O `git diff` vazio sozinho não prova a conversão (ver passo 2); por isso a comparação byte a byte com o `HEAD`.
- Fica de fora desta etapa, de propósito: mudar o `core.autocrlf` da máquina (não é preciso, o `.gitattributes` já manda) e criar `.editorconfig` ou configuração do VS Code (seria ferramenta nova; regra 4).
