# Plano da etapa 5.3: regras puras de adiamento em `xp.py`

## Contexto

As rotas de edição (5.9) e do botão Adiar (tarefa 7) vão precisar saber se a data está travada e qual é o novo contador de adiamentos. Esta etapa cria essas regras como funções puras, sem banco e sem rota, para que fiquem num lugar só e testadas (seção 4.2).

Ela também corrige um bug do `task_xp`: atraso negativo, ou seja, data no futuro, hoje aumenta o XP. Com 3 adiamentos e data 5 dias à frente, a conta dá `3 − 5 = −2`, o multiplicador vira 1,5 e uma tarefa difícil vale 75 XP em vez de 12. Ninguém chama essa função fora dos testes ainda, então o bug não afetou dados.

## Arquivos

Só estes dois: `backend/app/rules/xp.py` e `backend/tests/test_xp.py`.

## Mudanças em `backend/app/rules/xp.py`

1. **Import:** `from datetime import date`, da biblioteca padrão. Não é dependência nova.
2. **Comentário de `MAX_POSTPONEMENTS`:** passa a dizer também que, com 3 ou mais adiamentos efetivos, a data trava. O valor não muda.
3. **Três funções novas, e `task_xp` passa a usar a primeira:**

```python
# Soma os adiamentos manuais e os dias de atraso. Data no futuro não desconta adiamento.
def effective_postponements(manual_postponements: int, days_late: int) -> int:
    return manual_postponements + max(days_late, 0)


# Com 3 ou mais adiamentos efetivos, a data não pode mais ser mudada.
def is_due_date_locked(manual_postponements: int, days_late: int) -> bool:
    return effective_postponements(manual_postponements, days_late) >= MAX_POSTPONEMENTS


# Calcula o contador depois de mudar a data. Só mudar para depois conta como adiamento.
# Esta função não confere a trava: quem a chama precisa conferir antes.
def postponements_after_date_change(
    manual_postponements: int, days_late: int, current_due_date: date, new_due_date: date
) -> int:
    if new_due_date <= current_due_date:
        return manual_postponements

    return effective_postponements(manual_postponements, days_late) + 1
```

Em `task_xp`, a variável local passa a se chamar `effective`, para não ter o mesmo nome da função nova. O resto da função fica igual.

## Decisões

- **A função do contador recebe as duas datas**, e não um "sim/não" dizendo se a data foi para depois. Assim, a regra "antecipar e mandar a mesma data não contam" fica em `xp.py`, como pede a regra 9 do `CLAUDE.md`, e a rota não precisa repeti-la.
- **`days_late` continua sendo um número recebido de fora**, igual ao `task_xp` atual. Quem calcula os dias de atraso a partir de "hoje" é a etapa 5.9, com `app_today()`. Assim, `xp.py` não depende do relógio.
- **Antecipar nunca soma dias de atraso.** Uma tarefa atrasada não consegue ser antecipada, porque a nova data teria de ser anterior a hoje, e isso a API recusa com 422.

## Testes em `backend/tests/test_xp.py`

Os testes atuais não mudam. Entram estes:

| Função | Caso | Esperado |
| --- | --- | --- |
| `task_xp` | difícil, 0 adiamentos, atraso −1 | 50 (hoje dá 62) |
| `task_xp` | difícil, 3 adiamentos, atraso −5 | 12, ou seja, 25% (hoje dá 75) |
| `task_xp` | difícil, 3 adiamentos, 1 dia de atraso | 0 |
| `effective_postponements` | `(1, 2)` | 3 |
| `effective_postponements` | `(2, -5)` | 2 |
| `is_due_date_locked` | `(2, 0)`, `(1, 1)` e `(2, -5)` | destravada |
| `is_due_date_locked` | `(3, 0)`, `(0, 3)`, `(1, 2)` e `(4, 0)` | travada |
| `is_due_date_locked` | `(3, -5)`, o exemplo da seção 4.2 | travada |
| `postponements_after_date_change` | sem atraso, para depois, com contador 0, 1 e 2 | 1, 2 e 3 |
| `postponements_after_date_change` | `0 + 2 + 1`, atrasada movida para hoje | 3 |
| `postponements_after_date_change` | data no futuro, para mais longe, `(1, -5)` | 2 (o atraso negativo não desconta) |
| `postponements_after_date_change` | antecipar | contador igual |
| `postponements_after_date_change` | mesma data, com tarefa atrasada | contador igual |

O caso da mesma data garante a regra do "mesmo valor": editar outro campo de uma tarefa atrasada não soma os dias de atraso ao contador.

## Fora desta etapa

Calcular os dias de atraso a partir de `app_today()`, os códigos 409 e 422, e as rotas ficam para as etapas 5.4 a 5.9 e para a tarefa 7. A especificação e o `CLAUDE.md` não mudam.

## Como testar

Depois de eu aplicar as mudanças e rodar os testes, você confere com estes comandos, no PowerShell, a partir da raiz do projeto:

```powershell
.venv\Scripts\Activate.ps1
cd backend
pytest tests/test_xp.py
pytest
```

O primeiro `pytest` mostra as regras de XP, com os casos antigos e os novos. O segundo roda o projeto inteiro. Os dois devem terminar sem nenhuma falha. Como não há rota nova, nada muda no `/docs`.
