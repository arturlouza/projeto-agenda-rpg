# Plano da etapa 5.7: excluir tarefa

## Contexto

A API já cria e lista tarefas, mas ainda não exclui. Esta etapa cria `DELETE /tasks/{id}`.

O cuidado principal é o histórico de XP. A coluna `XpEntry.task_id` aponta para a tarefa, então:

- com a linha do histórico ainda apontando para a tarefa, a chave estrangeira recusa a exclusão;
- o XP já ganho precisa continuar somando, então a linha fica e só perde o vínculo (`task_id` nulo), como manda a seção 4.3.

## O que muda

Só dois arquivos, como a especificação prevê. Nenhuma dependência nova e nenhuma tabela alterada.

### 1. `backend/app/routers/tasks.py`

- Imports: acrescentar `Path` (de `fastapi`) e `XpEntry` (de `app.models`).
- Novo tipo do id, igual ao `TaskTypeId` de `task_types.py`:

```python
# Id que vem na rota. Fora deste intervalo, o FastAPI responde 422 sem consultar o banco.
TaskId = Annotated[int, Path(ge=1, le=MAX_ID)]
```

- Nova rota, no fim do arquivo, seguindo o padrão de `delete_task_type`:

```python
# O XP já ganho continua no histórico: as linhas da tarefa só perdem o vínculo com ela (seção
# 4.3). Tudo vale só no commit, numa única transação: se algo falhar no meio, nada muda no banco.
@router.delete(
    "/{task_id}",
    status_code=status.HTTP_204_NO_CONTENT,
    responses={404: {"description": "Tarefa não encontrada."}},
)
def delete_task(task_id: TaskId, session: SessionDep) -> None:
    task = session.get(Task, task_id)
    if task is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, detail="Tarefa não encontrada.")

    for entry in session.exec(select(XpEntry).where(XpEntry.task_id == task_id)).all():
        entry.task_id = None
        session.add(entry)

    # Envia as mudanças do histórico antes de excluir a tarefa, senão a chave estrangeira
    # poderia recusar a exclusão.
    session.flush()

    session.delete(task)
    session.commit()
```

**Decisões:**

- **Sem restrição por estado:** qualquer tarefa pode ser excluída, inclusive atrasada, travada ou concluída (seção 4.2).
- **Sem `get_task_or_404` por enquanto:** a busca só é usada aqui, então fica direto na rota. A função auxiliar pode nascer na 5.8, quando houver um segundo uso.

### 2. `backend/tests/test_tasks.py`

Importar `XpEntry` e criar um auxiliar `insert_xp_entry`, que grava uma linha direto no banco, porque gerar XP só chega na tarefa 6.

| Teste | O que prova |
| --- | --- |
| Excluir tarefa existente | Responde 204 sem corpo, e a tarefa some do banco e da lista do dia |
| Excluir em cada estado (pendente, atrasada, travada, concluída) | Todos dão 204 |
| Id desconhecido (`999`) e maior id aceito (`2147483647`) | Responde 404 |
| Id fora do intervalo (`0`, `-1`, `2147483648`, `10**30`) | Responde 422 |
| Excluir tarefa concluída com XP, havendo outra tarefa com XP | A soma não muda; a linha da excluída fica com `task_id` nulo e mantém valor e motivo; a linha da outra tarefa fica intacta |
| Falha simulada no `session.delete` | A tarefa continua no banco e a linha do histórico continua apontando para ela, o que prova a transação única |

## O que conferi antes de propor

Rodei a rota num protótipo temporário, com banco de teste e sem alterar nenhum arquivo do projeto:

| Versão da rota | Resultado |
| --- | --- |
| Como no plano | 204 sem corpo; linha da tarefa com `task_id` nulo; linha da outra tarefa intacta |
| Sem o laço que limpa o `task_id` | `IntegrityError`: a chave estrangeira recusa, então os testes pegam esse erro |
| Com um `commit` antes do `delete`, e falha no `delete` | O `task_id` fica nulo com a tarefa ainda no banco, então o teste da transação pega esse erro |
| Sem o `flush` | **Continua funcionando:** nenhum teste pega a retirada do `flush` |

**Sobre o `flush`:** mesmo assim ele fica, como a especificação pede. Não há `relationship` entre os modelos, então nada garante a ordem em que o banco recebe as mudanças sem ele. No protótipo a ordem saiu certa, mas isso não é garantia. O teste de XP ganha um comentário dizendo que não detecta essa retirada, como já fazemos nos testes de desempate.

**Situação atual:** 219 testes passando antes de qualquer mudança.

## Conceitos que vou explicar ao terminar

- Transação, e a diferença entre `flush` e `commit`.
- Por que o status 204 não tem corpo.
- Como `Path(ge=1, le=MAX_ID)` gera o 422 antes de a rota rodar.
- Como `monkeypatch` simula uma falha.


Depois, pelo `/docs`:

```powershell

```

1. Abra `http://localhost:8000/docs`.
2. Em `POST /tasks`, crie uma tarefa com a data de hoje e anote o `id`.
3. Em `GET /tasks/day/{day}`, peça o dia de hoje e veja a tarefa em `pending`.
4. Em `DELETE /tasks/{task_id}`, exclua pelo `id`: deve responder 204.
5. Repita o `GET`: a tarefa sumiu.
6. Repita o `DELETE`: deve responder 404.
