## As decisões

### 1. Como o JavaScript monta os cartões: `<template>` no HTML

O desenho do cartão fica no `index.html`, dentro de um `<template>`. O JavaScript copia o modelo com `cloneNode(true)`, acha cada parte com `querySelector` e preenche com `textContent`.

```html
<!-- Modelo do cartão de uma tarefa. O navegador não mostra o que está num <template>: o app.js
     copia este modelo para cada tarefa e preenche os textos. -->
<template id="task-card-template">
  <li class="task-card">
    <label class="task-check">
      <input type="checkbox" class="task-checkbox">
      <span class="task-check-name visually-hidden"></span>
    </label>
    <div class="task-body">
      <span class="task-title"></span>
      <span class="task-notes-icon" hidden><span aria-hidden="true">✎</span><span class="visually-hidden">Tem notas.</span></span>
      <span class="task-due-date" hidden></span>
      <span class="task-xp" hidden></span>
    </div>
  </li>
</template>
```

**Por que o `<template>`, e não `createElement`:**

- **O cartão se lê como HTML.** Com `createElement`, cada parte custa três linhas (criar, pôr a classe, encaixar no pai): uns 25 linhas de encanamento em que a estrutura do cartão some. Com o modelo, o JavaScript só tem as linhas que põem dados.
- **Cresce sem virar novelo.** A 10.3 acrescenta o botão do título, as notas e o Adiar: entram no modelo, mais duas ou três linhas de preenchimento. A tarefa 11 e a 12 seguem o mesmo padrão, com modelo próprio se o cartão for diferente.
- **Seguro e compatível com a CSP:** o conteúdo do `<template>` é inerte (não aparece, não roda script, não carrega imagem) e está no próprio `index.html`. Nenhum texto vira HTML: os dados entram só por `textContent`, então o teste que recusa `innerHTML` continua valendo.
- **O ponto fraco:** HTML e JavaScript ficam ligados pelos nomes das classes. Se uma classe mudar só num dos lados, o `querySelector` devolve `null` e o console mostra o erro na hora. O roteiro manual pega isso.

**Nome da caixinha para o leitor de tela:** o `<label>` envolve só a caixinha (o toque no título fica livre para a 10.3, e a seção 6.2 pede a caixinha separada do toque). Para a caixinha não ficar sem nome, o `<label>` leva o título num texto escondido da vista (`visually-hidden`), também por `textContent`. O leitor de tela lê "Ler 30 páginas, caixa de seleção, não marcada". Os outros caminhos (`aria-label` com o título, ou `aria-labelledby` com um id para cada título) seriam um jeito a mais de pôr dados na tela, ou dois ids por cartão.

**Conceitos novos:** `<template>` (um modelo de HTML que o navegador guarda sem mostrar); `cloneNode(true)` (copia um elemento com tudo o que tem dentro); `querySelector(".classe")` (acha, dentro do elemento, o primeiro filho com essa classe); `visually-hidden` (uma classe de CSS que esconde da vista, mas não do leitor de tela, diferente do `hidden`, que esconde de todos).

### 3. Voltar ao app: recarrega lista e topo quando a página volta a ficar visível

**Entra.** O app instalado pode ficar em segundo plano de um dia para o outro, e a tela mostraria o dia de ontem como se fosse hoje, com as atrasadas erradas. O evento `visibilitychange` avisa quando a página some ou volta; na volta, a tela pede `/tasks/today` e `/player` de novo. Nenhuma conta de data: o servidor diz que dia é.

```js
// Quando o app volta do segundo plano, pede a lista e o topo de novo. O servidor diz que dia é:
// se a meia-noite passou enquanto o app estava escondido, a tela já mostra o dia novo.
document.addEventListener("visibilitychange", function () {
  if (document.visibilityState === "visible") {
    refreshScreen();
  }
});
```

- **Sem "Carregando…" na volta:** a lista atual continua na tela até a nova chegar, sem piscar. O "Carregando tarefas…" aparece só ao abrir o app e no "Tentar de novo".
- **Se a volta falhar** (sem internet), a lista é trocada pelo aviso de erro com "Tentar de novo". Melhor do que deixar na tela uma lista que pode ser de ontem.
- **Efeito colateral bom:** trocar de aba no computador também recarrega. É assim que o roteiro manual confere o evento.

**Pedidos que se cruzam:** agora a mesma lista pode ser pedida por três caminhos (abrir, voltar ao app, depois da caixinha). Se dois pedidos se cruzarem e o mais antigo chegar por último, a tela ficaria com o estado velho. Cada função de carregar guarda o número do pedido mais recente e só desenha a resposta se ela for desse pedido:

```js
// Número do pedido mais recente da lista. Se dois pedidos se cruzarem, só o último é desenhado.
let latestDayRequest = 0;

async function loadDay() {
  latestDayRequest = latestDayRequest + 1;
  const thisRequest = latestDayRequest;
  try {
    const day = await apiRequest("tasks/today");
    if (thisRequest === latestDayRequest) {
      showDay(day);
    }
  } catch (error) {
    if (thisRequest === latestDayRequest) {
      console.error(error);
      showDayError();
    }
  }
}
```

O `loadPlayer` ganha o mesmo controle. A 10.4 vai precisar dele de qualquer jeito, com toques rápidos nas setas pedindo dias diferentes.

**Conserto no topo, por causa do recarregamento:** hoje o `catch` do `loadPlayer` escreve o erro mas não tira o `hidden` que o `showPlayer` pôs no sucesso anterior. Com um único carregamento isso não acontecia; com o recarregamento, um erro depois de um sucesso ficaria invisível. O `catch` passa a pôr `hidden = false`.

**Conceito novo:** `visibilitychange` é um evento do navegador que dispara quando a página fica escondida (outra aba, app em segundo plano, tela apagada) ou volta a aparecer; `document.visibilityState` diz qual dos dois.

### 4. Depois de concluir ou desmarcar: os dois pedidos saem juntos

**Fluxo da caixinha:**

```js
// Enquanto uma caixinha espera a resposta, todas ficam bloqueadas (uma gravação por vez).
let saving = false;

async function toggleTask(task) {
  saving = true;
  disableAllCheckboxes();
  hideSaveMessage();

  // A ação vem do que o servidor mandou na lista, não do desenho da caixinha.
  const action = task.completed ? "uncomplete" : "complete";
  try {
    await apiRequest("tasks/" + task.id + "/" + action, { method: "POST" });
  } catch (error) {
    // 409: a tela estava desatualizada. Recarregar resolve, então não há mensagem.
    if (error.status !== 409) {
      console.error(error);
      showSaveMessage();
    }
  }

  saving = false;
  await refreshScreen();
  focusTask(task.id);
}

// Pede a lista e o topo ao mesmo tempo. Cada um trata o próprio erro.
async function refreshScreen() {
  await Promise.all([loadDay(), loadPlayer()]);
}
```

- **Juntos, com `Promise.all`:** a lista e o topo não dependem um do outro, então pedir os dois ao mesmo tempo deixa a espera igual à do mais lento, e não à soma dos dois. Cada um já trata o próprio erro (a lista mostra "Tentar de novo"; o topo, a linha de erro dele), então um não impede o outro.
- **A caixinha tocada:** o navegador já a marca (ou desmarca) no toque, e ela fica `disabled` até a resposta. Depois, a lista é desenhada de novo com o que o servidor diz: no sucesso, a tarefa muda de seção; no erro, a caixinha volta ao estado real.
- **Todas as caixinhas bloqueadas, não só a tocada:** a lista inteira é desenhada de novo depois de cada gravação. Se só a tocada ficasse bloqueada, tocar numa segunda tarefa logo em seguida deixaria a gravação dela em andamento enquanto o desenho da primeira troca a caixinha dela por uma nova, desbloqueada e com o estado antigo; um terceiro toque mandaria outro pedido. Com uma gravação por vez, isso não acontece, com uma variável só (`saving`). Cada cartão novo nasce com `checkbox.disabled = saving`. A espera é curta, e o servidor continua protegido contra XP em dobro de qualquer jeito (tarefa 6).
- **O foco do teclado:** desenhar a lista de novo remove a caixinha que tinha o foco, e o foco cairia no começo da página. Depois de recarregar, `focusTask` devolve o foco à caixinha da mesma tarefa, onde ela estiver agora. Se ela foi para "Concluídas" e a seção está fechada, o foco vai para o `<summary>` "Concluídas (N)". Se a tarefa sumiu da lista (excluída em outra tela, ou o dia virou), o foco fica onde o navegador puser. No toque com o dedo, o Chrome não desenha o anel de foco, então nada muda para quem não usa teclado.

```js
// Devolve o foco à caixinha da tarefa depois de desenhar a lista de novo.
function focusTask(taskId) {
  const checkbox = document.getElementById("task-check-" + taskId);
  if (checkbox === null) {
    return;
  }
  if (completedSection.contains(checkbox) && !completedSection.open) {
    completedSummary.focus();
  } else {
    checkbox.focus();
  }
}
```

- **A mensagem de erro ao salvar** ("Não foi possível salvar. Tente de novo.") fica no **topo fixo**, logo abaixo da linha do nível, para ser vista mesmo com a lista rolada até as Concluídas. Some no próximo toque numa caixinha. É uma linha calma, na cor de erro, com `role="status"`.
- **`apiRequest` passa a guardar o código da resposta** em `error.status`, como manda a especificação, para a tela reconhecer o 409 sem ler texto. Erro de rede não tem código (`error.status` fica `undefined`) e cai no "Não foi possível salvar".
- **`fetch` no modo padrão,** sem corpo, como pede a seção 6.7. O navegador manda o `Origin` sozinho, o que a tarefa 15 vai exigir.

**Conceitos novos:** `Promise.all` (espera várias tarefas assíncronas que andam ao mesmo tempo); `addEventListener("change", ...)` (roda uma função quando a caixinha muda); a função dentro do `addEventListener` "lembra" a tarefa do cartão em que foi criada (isso se chama *closure*), por isso `toggleTask(task)` sabe qual tarefa mandar.

### 5. A data marcada no cartão das atrasadas

```js
// Escreve a data "2026-11-01" como "01/11/2026", sem conta de data. new Date("2026-11-01") é
// meia-noite em UTC; formatada no fuso do celular (Brasília), viraria 31/10/2026. Com o
// timeZone "UTC", sai o mesmo dia que está no texto.
const dueDateFormat = new Intl.DateTimeFormat("pt-BR", {
  timeZone: "UTC",
  day: "2-digit",
  month: "2-digit",
  year: "numeric",
});

function formatDueDate(text) {
  return dueDateFormat.format(new Date(text));
}
```

O cartão da atrasada mostra "Marcada para 01/11/2026", com o ano, porque uma atrasada pode ser do ano anterior. Só as atrasadas mostram a data: `createOverdueCard` chama `createTaskCard` e acrescenta a data. Assim o JavaScript nunca compara datas para decidir se mostra. O roteiro manual usa uma tarefa de **01/11**, porque com o erro ela apareceria como 31/10, mudando até o mês, o que é fácil de ver.

### 6. Três detalhes de tela que a especificação não fixa

- **Títulos das seções:** "Atrasadas" (com a cor de aviso na borda) e "Hoje", para as pendentes não parecerem atrasadas quando as duas aparecem. Cada seção some quando a lista dela está vazia; "Concluídas (N)" some com zero concluídas. Na 10.4, o título "Hoje" passa a mostrar o dia escolhido.
- **"Concluídas" aberta ao recarregar:** sai de graça. O JavaScript esvazia e preenche só as `<ul>`, e o `<details>` continua o mesmo elemento, com o mesmo `open`. Ao abrir o app, ele nasce fechado, porque o HTML não tem `open`.
- **"+N XP" com zero:** uma concluída que vale 0 mostra "+0 XP". É o que ela rendeu, e a seção 4.4 já trata essa tarefa como concluída que não rendeu nada.

## Testes

**Os 619 atuais continuam passando,** inclusive `test_javascript_never_writes_html_or_evaluates_text`.

**Teste novo em `backend/tests/test_frontend.py`: o HTML não tem código dentro da página.** Entra. A CSP já bloqueia script inline e `onclick` no navegador, mas bloqueia **em silêncio**: o botão simplesmente não funciona, e o pytest não perceberia. Com o `<template>`, o HTML passa a ter mais tags, e o teste garante que nenhuma escorrega.

O teste usa o `HTMLParser`, da biblioteca padrão do Python (sem dependência nova), que lê o HTML como o navegador lê. Uma expressão regular erraria casos que ele acerta: atributo em maiúsculas (`onClick`), com ou sem aspas, ou um `onclick` escrito dentro de um comentário, que não roda.

```python
from html.parser import HTMLParser

# Lê o HTML e anota o que a CSP bloquearia sem aviso: script dentro da página, atributos
# on... (onclick, onerror) e estilo dentro da página. O HTMLParser entrega os nomes dos
# atributos em minúsculas e pula os comentários.
class InlineCodeFinder(HTMLParser):
    def __init__(self):
        super().__init__()
        self.problems = []
        self.inside_script = False

    def handle_starttag(self, tag, attrs):
        names = [name for name, value in attrs]
        for name in names:
            if name.startswith("on") or name == "style":
                self.problems.append(f"<{tag}> com o atributo {name}")
        if tag == "style":
            self.problems.append("<style> dentro da página")
        if tag == "script":
            self.inside_script = True
            if "src" not in names:
                self.problems.append("<script> sem src")

    def handle_endtag(self, tag):
        if tag == "script":
            self.inside_script = False

    def handle_data(self, data):
        if self.inside_script and data.strip():
            self.problems.append("código dentro de <script>")


def test_html_has_no_inline_code():
    html_files = sorted(FRONTEND_DIR.rglob("*.html"))
    assert html_files

    for html_file in html_files:
        finder = InlineCodeFinder()
        finder.feed(html_file.read_text(encoding="utf-8"))
        finder.close()
        assert finder.problems == [], f"{html_file.name}: {finder.problems}"
```

- **Um pouco além do pedido:** o teste também recusa `<style>` e o atributo `style=` no HTML, porque a CSP (`style-src 'self'`) os bloqueia do mesmo jeito silencioso. O `element.style.backgroundColor` que a tarefa 11 vai usar não é afetado: é JavaScript mexendo no estilo, não estilo escrito no HTML.
- **Conceito novo:** o `HTMLParser` lê o texto e chama um método para cada parte que encontra (`handle_starttag` para `<li class="...">`, `handle_endtag` para `</li>`, `handle_data` para o texto entre as tags). A classe herda dele e escreve só esses três métodos.

**Prova de que os testes pegam o erro:** tiro por um momento, um de cada vez, e vejo o teste falhar: um `onclick="x"` no `<template>`; um `<script>alert(1)</script>`; um `style="color: red"`; um `innerHTML` no `app.js`. Um comentário `<!-- onclick= -->` não pode reprovar. Desfaço cada um e confiro por hash que os arquivos voltaram iguais. Espero **620 testes** e digo o número exato no resumo.

O JavaScript não tem teste automático (o projeto não usa ferramenta de teste de navegador, e uma seria dependência nova). Ele fica coberto pelo roteiro manual abaixo.

## Como você vai testar

Na pasta `backend`, com o ambiente virtual ativo:

```powershell
pytest
pytest tests/test_frontend.py -v
```

**Preparação: um banco só para o roteiro.** Com o servidor desligado, separe o banco de desenvolvimento (o `*.db` fica fora do Git):

```powershell
Rename-Item agenda.db agenda-reserva.db
uvicorn app.main:app --reload
```

O app cria um `agenda.db` vazio ao subir. Abra `http://localhost:8000/` no Chrome, com o F12 aberto.

1. **Dia vazio:** aparece "Nenhuma tarefa para hoje.", sem os títulos "Atrasadas", "Hoje" e "Concluídas".
2. **Carregando:** na aba **Network**, troque "No throttling" por "3G" e recarregue: "Carregando tarefas…" aparece antes da lista. Volte para "No throttling".
3. **Erro e "Tentar de novo":** na aba **Network**, clique com o botão direito no pedido `today` e escolha **Block request URL**. Recarregue: aparece "Não foi possível carregar as tarefas." com o botão. Desbloqueie (botão direito, **Unblock**) e toque em "Tentar de novo": a lista volta.
4. **Criar as tarefas:** em `http://localhost:8000/docs`, crie com `POST /tasks` três tarefas para hoje: uma `medium` sem notas, uma `easy` com notas e uma com o título `<img src=x onerror=alert(1)>`. Para a atrasada, que a API não deixa criar, rode num segundo PowerShell, na pasta `backend`, com o ambiente virtual ativo (o texto fica sem acento de propósito: o PowerShell 5.1 estraga acentos ao passar texto para o Python):

   ```powershell
   @'
   from datetime import date
   from sqlmodel import Session
   from app.database import engine
   from app.models import Task
   with Session(engine) as session:
       session.add(Task(title="Atrasada de teste", due_date=date(2026, 11, 1), difficulty="medium"))
       session.commit()
   '@ | python -
   ```

5. **Voltar ao app (`visibilitychange`):** volte à aba do app **sem recarregar**: as tarefas aparecem sozinhas, e a aba **Network** mostra os pedidos `today` e `player` no momento da volta.
6. **Lugares certos:** "Atrasada de teste" na seção "Atrasadas", com borda de aviso e "Marcada para 01/11/2026"; as três de hoje em "Hoje", na ordem em que foram criadas; a que tem notas mostra o ✎.
7. **A data não volta um dia:** compare com `http://localhost:8000/tasks/today`: o `due_date` é `2026-11-01` e o cartão diz 01/11/2026, não 31/10/2026. Para ver por que o `timeZone: "UTC"` importa, digite no **Console**: `new Date("2026-11-01").toLocaleDateString("pt-BR")` dá 31/10/2026 no fuso de Brasília. Depois, com Ctrl+Shift+P, digite "Show Sensors", escolha **San Francisco** em **Location** e recarregue: o cartão continua 01/11/2026. Escolha **Tokyo** e recarregue: continua 01/11/2026, nem um dia depois. Volte para **No override**.
8. **Título em forma de HTML:** `<img src=x onerror=alert(1)>` aparece escrito como texto, sem alerta, e a aba **Network** não mostra nenhum pedido para `x`.
9. **Concluir:** anote o topo. Marque a caixinha da `medium` de hoje: ela sai de "Hoje", aparece "Concluídas (1)" fechada, e o topo sobe 25 XP. Abra "Concluídas": a tarefa está marcada, riscada, mais transparente e com "+25 XP".
10. **Concluídas continua aberta:** com "Concluídas" aberta, conclua a `easy`: a seção continua aberta, agora com (2) e "+10 XP". Toque em "Concluídas" para fechar e de novo para abrir.
11. **Desmarcar:** desmarque a `medium` em "Concluídas": ela volta para "Hoje", e o topo fica 10 XP acima do valor anotado no passo 9 (só a `easy` continua concluída).
12. **Toque duplo:** com "3G" na aba **Network**, dê um clique duplo rápido na caixinha da atrasada. A aba **Network** mostra **um** `complete` só; enquanto ele espera, todas as caixinhas ficam bloqueadas. O topo sobe uma vez só. Volte para "No throttling".
13. **Tela desatualizada (409):** abra o app em duas janelas lado a lado (as duas visíveis, para o `visibilitychange` não recarregar). Na janela A, desmarque uma tarefa concluída. Na janela B, que ainda a mostra concluída, desmarque a mesma: a lista da B se atualiza, sem mensagem de erro, e a aba **Network** da B mostra o `uncomplete` com 409.
14. **Erro ao salvar:** na aba **Network**, bloqueie o padrão `*complete*` (Block request URL, depois edite o padrão no painel **Network request blocking**). Marque uma caixinha: aparece no topo "Não foi possível salvar. Tente de novo." e a caixinha volta a ficar desmarcada. Desbloqueie e marque de novo: a mensagem some e a tarefa é concluída.
15. **Teclado:** recarregue e use Tab até uma caixinha de "Hoje" (o anel de foco aparece) e aperte Espaço. Com "Concluídas" fechada, o foco vai para "Concluídas (N)"; abra com Enter, vá até a tarefa com Tab e aperte Espaço para desmarcar: o foco segue a caixinha da tarefa, de volta em "Hoje".
16. **Celular:** Ctrl+Shift+M, largura de 360 px. Sem rolagem para o lado, nem com um título de 100 letras sem espaço (crie um pelo `/docs`). Caixinha, "Concluídas" e "Tentar de novo" fáceis de tocar. Repita os passos 9 e 10 no modo celular.
17. **Console limpo:** nenhum erro vermelho além do 404 do `favicon.ico` e dos erros que os passos 3, 13 e 14 provocaram de propósito.

**No fim**, com o servidor desligado, escolha: manter o banco do roteiro, ou voltar ao seu (`Remove-Item agenda.db` e `Rename-Item agenda-reserva.db agenda.db`).

**A virada da meia-noite** não dá para testar sem esperar: o passo 5 prova que a volta ao app pede `/tasks/today` de novo, e os testes da 10.1 provam que essa rota troca de dia à meia-noite de Brasília.
